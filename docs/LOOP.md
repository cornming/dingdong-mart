# Loop engineering：這個專案怎麼一圈一圈做

每一圈都走同樣六步，走完才算一圈：

1. **輪廓**：這一圈要解決什麼，一句話說清楚。
2. **深入**：把輪廓拆成具體要改的東西。
3. **定案**：寫下這一圈的範圍，超出範圍的放進「下一圈候選」。
4. **批判**：實際看畫面、讀數字，找出哪裡不對、哪裡不像當年的感覺。
5. **改進**：動手改。
6. **驗證**：三道閘門全部通過，才能提交。

## 三道驗證閘門

| 閘門 | 指令 | 擋什麼 |
|---|---|---|
| 規則測試 | `npm test` | 規則寫錯：現金對不起來、庫存變負數、存檔讀回來不一樣、事件當掉 |
| 平衡模擬 | `npm run balance` | 數值失衡：放著不管也能拿牌、用心玩卻破產、金牌太容易 |
| 介面實測 | `npm run smoke` | 介面壞掉：JavaScript 錯誤、版面橫向溢出、按了沒反應、存檔讀不回來 |

介面實測會留下截圖。截圖一定要人（或 AI）實際看過——選單按鈕的字跟底色一樣這種問題，測試是綠的，只有看圖才會發現。

推到 `main` 時，GitHub Actions 會自動跑這三道閘門，通過才會升版與部署。

## 什麼時候算「完成」

- 三道閘門全過。
- 截圖逐張看過，沒有破版、沒有看不懂的地方。
- 新手不看說明，第一天結算後知道下一步該做什麼。
- 批判清單裡沒有「會讓人不想玩下去」等級的問題。

## 下一圈候選

依「對手感的幫助 ÷ 工作量」排序，還沒做：

1. 營業中可以做的小動作（例如親自打掃、喊促銷），讓白天不只是看。
2. 商品圖示：目前貨架上是色塊，換成每種商品的像素小圖。
3. 廠商促銷時的進貨折扣目前不會反映在當日淨利上（現金是對的），報表應該另列一行。
4. 第二種遊戲模式：不限天數的「連鎖店」，賺夠了可以開第二家。
5. 音樂只有一首，加一首夜間版。
